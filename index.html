MQTT

简述

MQTT（Message Queuing Telemetry Transport，消息队列遥测传输协议），是一种基于发布/订阅（publish/subscribe）模式的”轻量级”通讯协议，该协议构建于TCP/IP协议上，由IBM在1999年发布。MQTT最大的优点在于，可以用极少的代码和带宽，为远程连接的设备提供可靠的消息服务。作为一种低开销、低带宽占用的即时通讯协议，在物联网、小型设备和移动应用等方面有着比较广泛的应用。

设计规范

由于物联网的环境是非常特别的，所以MQTT遵循以下设计原则：

  1. 精简，不添加可有可无的功能
  2. 发布/订阅（Pub/Sub）模式，方便消息在传感器之间传递
  3. 允许用户动态创建主题，零运维成本
  4. 把传输量降到最低以提高传输效率
  5. 把低带宽、高延迟、不稳定的网络等因素考虑在内
  6. 支持连续的会话控制
  7. 理解客户端计算能力可能很低
  8. 提供服务质量管理
  9. 假设数据不可知，不强求传输数据的类型与格式，保持灵活性

版本

MQTT主要由两个版本：V3、V5。V5是在V3版本上做的升级，所以完全兼容V3，建议使用V5版本，可以使用更加完善的功能。

特性

  1. 使用发布/订阅信息模式，提供一对多的信息发布，使应用程序之间解耦。

  2. 屏蔽负载内容的信息传输。

  3. 使用TCP/IP提供网络连接

    MQTT协议处于应用层协议，而传输层协议还是使用的TCP/IP协议。但也有基于UDP的版本，MQTT-SN。

  4. 有三种消息发布服务质量QoS（Quality of Service）

    只有一次（Qos0）：消息只发送一次

    消息只发送一次，不管是否发送成功。发送端不会检查发送的消息是否被正确接收。

    在网络极其稳定的情况下，一般不会出现问题。但大多数情况网络情况会受多种因素干预，不能保证消息被正常的接收。所以比较适用于传输不重要消息的场景

    至少一次（Qos1）：消息最少发一次

    消息至少会发送一次，发送端需要等待接收端返回PUBACK报文确认报文。由于回应报文处于网络原因长时间接收不到，发送端会再次发送一次消息，直到收到确认报文。

    接收端会出现收到重复消息的情况，所以需要保证幂等。

    至多一次（Qos2）：保证消息收到一次

    确保接收端只接收一次消息，但发送的过程变的更加复杂，需要两次消息确认。因此，Qos2是最安全的服务等级，也是效率最低的，可以用来传输重要的数据。

    1. 发送端发送消息给Broker
    2. Broker收到发送端发送的消息，返回PUBREC给发送端，代表我收到消息了
    3. 发送端接收到PUBREC之后，发送PUBREC，表示此次发送结束
    4. Broker收到PUBREC，返回PUBCOMP给发送端，表示结束了，我知道了。

  5. 小型传输，费用小(固定长度的头部为2字节)，协议交换最小化，减少网络流量

  6. 使用LastWill和Testament特性，通知各客户端异常中断的机制

实现方式

MQTT协议中三种身份：发布者（Publish）、代理（Broker）、订阅者（Subscribe）。发布者和订阅者都是属于客户端，代理属于服务器端。

MQTT传输的消息分为两部分：

  • Topic，跟消息队列的Topic类似，订阅者可以订阅改主题的消息，一旦发布者生产了此主题的消息，订阅者会收到此消息。
  • payload，订阅者具体要使用的内容，也就是消息的内容。

MQTT客户端

  • 发布其他客户端可能会订阅的信息
  • 订阅其他客户端发布的消息
  • 退订或删除应用程序的消息
  • 断开与服务器的连接

MQTT服务端

  • 接收来自客户端的网络连接
  • 接收客户端发布的消息
  • 处理客户端的订阅和退订
  • 转发消息

订阅、会话、主题

  • 订阅（Subscription）

    一个会话可以包含多个订阅。每一个会话中的每个订阅都有一个不同的主题筛选器。

  • 会话（Session）

    服务器与客户端连接之后就是一个会话了，会话包含了多个连接。

  • 主题名（Topic Name）

    消息的一个标签，代表此消息是干什么的。如订阅空调的温度，那么订阅温度就是一个主题了。

  • 主题筛选器（Topic Filter）

    对主题的通配符进行筛选，可以匹配对应的主题

  • 负载（Payload）

    消息内容

MQTT协议数据包结构

MQTT协议中，一个MQTT数据包有三部分组成：固定头、可变头、消息体。

  • 固定头，存在所有的MQTT数据包中，表示数据包类型以及数据包的分组类标识。
  • 可变头，存在于部分MQTT数据包中，数据包的类型决定了数据包中是否有可变头。
  • 消息体，存在于部分的MQTT数据包中，也就是实际的内容。

Netty

简介

Netty 是由 JBOSS 提供的一个 Java 开源框架。Netty 提供异步的、基于事件驱动的网络应用程序框架，用以快速开发高性能、高可靠性的网络 IO 程序,是目前最流行的 NIO 框架，Netty 在互联网领域、大数据分布式计算领域、游戏行业、通信行业等获得了广泛的应用，知名的Elasticsearch、Dubbo 框架内部都采用了 Netty。

为啥要使用Netty

Netty基于Java NIO类库开发的一个网络框架。相较于传统的BIO（Blocking IO）同步阻塞IO有着更高的吞吐量、并发量，从而拥有更高的性能。像社交软件类的需要实时通讯系统，使用Netty服务器，并配合合适的系统架构，可以极大的提高服务器的性能。

Netty是一个网络框架，如果我们直接使用Java提供的NIO实现业务，往往会耗费很大的人力。想想网络的断线重连、数据的拆包、数据的粘包等问题，不重复造轮子才是好的选择，在这Netty框架以及很成熟了，咱们直接使用就好。当然Java的NIO咱们还是要复习一下，这样能更快的入门Netty。

Linux的5种IO模型

首先说明几个概念：

  • 阻塞

    坐飞机过安检时，正在玩手机的你，需要把手机上交。然后你需要站在小台面上，等待安检工作人员进行检查，在检查的过程中，你是无法玩手机的。那么可以说你在被检查时，是阻塞的（单指玩手机的动作）。当安检人员检查完成之后，你又可以拿起你的手机进行玩耍了。

  • 非阻塞

    放假在家玩游戏很嗨的你，突然肚子饿了，然后告诉妈妈说啥时候做饭，妈妈说现在就做。然后你就又继续玩游戏了，玩了一会肚子咕咕叫，你跑去厨房问饭做好了吗，妈妈说还得一会，然后你又返回房间继续玩游戏。玩游戏这个动作对你来说是不阻塞的，因为你不会被妈妈叫住，而是从妈妈口里面得出饭是否做出的结果，没做好反时你继续玩游戏，做好饭了你就可以去吃饭了。非阻塞是继续不停的轮询获取指令的执行结果。

  • 同步

    还是你在房间玩游戏，你不停问妈妈饭做好了吗，注意此时的对象是你本身，你需要靠自己去获取饭是否做好的信号。发起方和接收方是一个人，这就是同步。

  • 异步

    你在房间玩手机，你告诉妈妈饭做好之后叫我，然后你继续玩游戏，当妈妈做好饭之后，她主动叫你去吃法。这个结果不是你主动询问的，而是妈妈告诉你的。发起放和接收方不是一个人，这就是异步。

同步阻塞IO（Blocking IO）

阻塞IO一般指的是用户态必须等到内核态执行完一系列操作之后，操作系统从内核态切换回用户态，此时程序才能继续执行。在内核执行指令期间，用户态是不能进行任何操作的。Java中创建的普通的Socket默认就是同步阻塞的。

流程如上图：

  1. 应用程序调用Read函数，调用此函数的线程进入阻塞状态。
  2. 此时内核会准备数据，但由于没有可读的数据返回（可能由于Sokcet没有收到任何数据包），所以用户态的线程一直在阻塞，什么都干不了。
  3. 内核检测到了数据（Socket有数据到达），将数据从内核缓冲区拷贝到用户缓冲区，read函数返回，应用程序不在阻塞，继续完成其它事情。

阻塞IO优缺点

  • 缺点：程序需要为每个连接都创建一个线程，线程获取数据时是阻塞的。当连接数很大时，创建的线程也会变多，没创建一个线程都需要内存空间，甚至很多线程处于阻塞状态，无法重复利用服务器资源。
  • 优点：实现起来简单。

同步非阻塞IO（Non-Blocking IO，NIO）

阻塞IO一般指的是用户态等待内核执行指令的过程中，可以不断的寻轮指令是否执行完成。如果没有执行完成，你可以继续去干其它事情。此IO又叫NIO，但Java中的NIO包并不是基于同步非阻塞IO去实现的，而是基于IO多路复用模型。

流程如上图：

  1. 应用程序调用Read函数，此时没有可读数据，Read函数立马返回，应用程序继续做其它事情。
  2. 应用程序轮询第二次调用Read函数，依旧没有客服数据，Read函数立马返回，就这样重复轮询调用。
  3. 当内核有数据时，会将数据复制到用户缓冲区，当下一次Read函数调用时，会返回有可读数据，至此一次读取操作完成。

非阻塞IO优缺点

  • 缺点：需要应用程序端不停轮询进行系统调用，频繁的进行上下文切换。
  • 优点：应用程序的调用线程只需要阻塞在Read函数调用开始以及返回时，不会一直阻塞，当可读数据时，应用程序的调用线程可以去干其它事情。

IO多路复用（IO Multiplexing）

传统的IO模型，在用户每次发起一个请求的时候，服务器都需要创建一个线程，后续客户端与服务器没有任何交互，此线程就处于空闲时间，使得服务器的资源没有得到充分的利用。为了提高性能，操作系统引入了一种新的系统调动。首先会有一个线程管理多个用户的连接请求，轮询的检查用户连接的状态（检查IO的文件描述符），若有连接进行读或写操作，操作系统会返回此文件描述符，应用程序可以使用此文件描述符进行后续操作。比如select、poll、epoll系统调用。

流程如上图：

  1. 应用程序将Read操作的文件描述符（Socket连接）注册到Linux的select/epoll选择器中（此时调用的线程处于阻塞状态），Java对应Selector类。然后，开启一个线程寻轮检查连接是否有可读事件（可以是写、连接等事件）发生。
  2. 轮询检测到可读事件时，代表注册过的socket连接上有可读的数据。内核会返回可读的socket列表（select/epoll实现不一样）给应用程序。
  3. 应用程序循环处理socket列表，调用Read函数（此时调用的线程是阻塞的），内核将内核缓冲区的数据复制到用户缓冲区。
  4. 复制完成后，内核返回结果，用户端调用线程解除阻塞状态，继续执行其它事情。

IO多路复用的优缺点

  • 缺点：Select/Epoll系统调用还是处于阻塞状态，有可读数据之后，使用Read函数也是处于阻塞状态。
  • 优点：不需要在用户态轮询查询IO是否处于就绪状态，内核会自己轮询检测就绪状态，减少了系统调用的次数。可以同时处理更多的网络连接，不需要为每个连接创建一个线程，只需要用少量的线程轮询查询IO状态即可。

select：select有连接数量限制，为1024个。select函数返回后，需要通过遍历所有的文件描述符，因为他不知道具体是哪个IO流实践发生。

poll：解决了1024个连接限制的问题，但还是需要遍历所有的文件描述符，来获取已经就绪的socket。

epoll：无需遍历所有的文件描述符，而是通过事件回调机制，只处理就绪状态的socket。

信号驱动 IO 模型

信号驱动IO向内核发送一个信号（调用sigaction的时候建立一个SIGIO的信号），然后应用用户进程可以去做别的事，不用阻塞。当内核数据准备好后，再通过SIGIO信号通知应用进程，数据准备好后的可读状态。应用用户进程收到信号之后，可以调用Read函数获取数据。

无论是BIO、NIO还是IO多路复用，在调用Read函数获取数据时，应用程序都会处于阻塞状态，那么有什么IO可以解决？答案是异步IO。

异步IO（Asynchronous IO，AIO）

应用程序进行系统调用，请求内核获取数据。应用程序只是告知一下内核，就可以去继续干其它事情了，当操作系统有数据之后，会将数据复制到用户态缓冲区，并通知应用程序处理完成。

Java中的IO

Java的传统IO是基于BIO实现的，也就是基于同步阻塞IO。Java的NIO不是基于Linux的NIO实现的，而是基于IO多路复用实现的。

Java的NIO2也就是异步IO，对应操作系统的AIO。

Reactor模型

简介

Reactor模式（反应堆模式）是一种基于事件驱动的模式，适合做海量数据的事件，属于同步非阻塞的一种NIO实现模式。对IO线程处理的过程分而治之，基于IO多路复用模型对IO事件进行注册以及监听，将监听到的事件交由相应的处理器进行处理。

组成部分

  1. Reactor：负责监听和分发事件
  2. Handlers：处理器，负责处理各种不同的事件

工作流程

  1. 应用程序将需要处理的事件（读、写等）和对应的处理器注册到Reactor
  2. Reactor开始监听所注册的事件
  3. 当某个事件源发生事件之后，Reactor将事件分发给对应的处理器
  4. 处理器处理相应的事件

Netty的Reactor线程模型

Reactor单线程模型

Reactor单线程模型整个过程使用的都是一个用户线程，从轮询监听客户端连接、读、写等事件，到处理读写等事件，都使用一个线程完成。

缺点:

  • 无法重复利用服务器的多核CPU，并且监听事件和处理事件逻辑高度耦合。
  • 处理业务逻辑时，耗时比较长时，无法处理下一个客户的连接或读写等请求。

Reactor多线程模型

为了提高处理事件的速度，创建了一个Worker线程池，异步处理读、写等事件，并将处理的结果返回给上层。

缺点：

虽然业务处理逻辑重复利用了多核CPU资源，但在进行读、写系统调用时，用户线程仍处于阻塞状态，无法处理下一个客户端连接，影响系统的并发性以及吞吐量。

主从Reactor多线程模型

将客户端的连接事件交给Reactor主线程负责，读写事件交由Reactor从线程负责，业务逻辑处理依旧是一个Worker线程池。主从模式相较于Reactor多线程模型，将阻塞的读、写系统调用与客户端监听事件解耦。让主线程专注于客户端连接事件，而从线程专注读写事件。这样可以同一时间内接收更多的用户连接，进而提高系统性能。

Reactor主线程、Reactor从线程可升级为线程池。

Linux

简介

Linux 内核最初只是由芬兰人林纳斯·托瓦兹（Linus Torvalds）在赫尔辛基大学上学时出于个人爱好而编写的。

Linux 是一套免费使用和自由传播的类 Unix 操作系统，是一个基于 POSIX 和 UNIX 的多用户、多任务、支持多线程和多 CPU 的操作系统。

Linux 能运行主要的 UNIX 工具软件、应用程序和网络协议。它支持 32 位和 64 位硬件。Linux 继承了 Unix 以网络为核心的设计思想，是一个性能稳定的多用户网络操作系统。

发行版

目前市场比较有名的发行版：Ubuntu、RedHat、CentOS、Debian、Fedora、SuSE、OpenSUSE、Arch Linux、SolusOS 等。

Linux vs Windows

Windows界面统一，驱动程序丰富，版本更新频繁。使用比较简单，很适合普通人群使用。比较多的用于办公室办公、学习等。

Linux的界面风格随发行版，可能也互不兼容。GNU/Linux 的终端机是从 UNIX 传承下来，基本命令和操作方法也几乎一致。比较多的用于服务器。

内核引导

计算机打开电源后，会对BIOS（基本输入输出系统）进行开机自检，按照BIOS设置的启动设备（一般是硬盘）进行启动。操作系统接管硬件之后，会读入 /boot 目录下的内核文件。

运行init

init程序会去读取配置文件 /etc/inittab。用来引导启动其它进程。

运行级别

Linux系统有7个运行级别，根据不同的场景，从而分配不同的开机启动程序。

  • 运行级别0：系统的停机状态，若设置为此运行级别，则系统将不能启动。
  • 运行级别1：单用户的工作状态，只有root权限，适用于系统维护，并且不能远程登录。
  • 运行级别2：多用户的状态。没有NFS。
  • 运行级别3：完全的多用户状态，有NFS。登录后进入控制台模式。
  • 运行级别4：保留。
  • 运行级别5：登录后进入GUI模式，也就是图形界面。
  • 运行级别6：系统重启模式，若设置此级别，则系统陷入重启循环。

系统初始化

Init会调用执行 /etc/rc.d/rc.sysinit，而rc.sysinit是一个bash shell脚本，主要完成一些系统初始化的工作。激活交换分区、检查磁盘、加载硬件模块以及其它需要优先执行的任务。/etc/rc.d/rc5.d/目录中的启动脚本其实是一些连接文件，真正的rc启动脚本在/etc/rc.d/init.d/下。

我们可以在/etc/rc.d/init.d下添加我们自定义的启动脚本。

RocketMQ部署方式

单Master

只有一个Broker，一旦重启或者宕机，对外就无法提供服务，建议线上不要使用。

多Master

一个集群没有Slave，都是Master。可以是2个或3个节点。

  • 优点：配置简单，相比于单节点，可以同时保存并处理更多消息，提高并发。

  • 缺点：一个节点宕机之后，此节点的消息在恢复之前无法被消费。

多Master多Slave异步复制

每个Master有一个Slave，有多对Master-Slave。HA采用异步复制，主备消息不同步，呈现最终一致性。

  • 优点：当Master节点宕机之后，消费者可以在Slave上继续消费消息，切换操作不需要人工干预。性能同多Master模式几乎一样

  • 缺点：在Master节点宕机之后会有消息丢失。

多Master多Slav同步双写

每个Master有一个Slave，有多对Master-Slave。采用同步复制，主从数据一致。

  • 优点：数据与服务都无单点故障，Master宕机情况下，消息无延迟，服务可用性与数据可用性都非常高；
  • 缺点：性能比异步复制模式略低（大约低10%左右），发送单个消息的RT会略高，且目前版本在主节点宕机后，备机不能自动切换为主机。

自动主从切换（5.0版本）

相比于主从模式，添加了基于 Raft 的一致性模块（DLedger Controller），当Master节点宕机之后，可以自主实现主从切换。

特性

消息的订阅与发布

消息发布的意思是生产者向Broker的某个Topic发送消息。

消息订阅的意思是消费者订阅了某个Topic中带有Tag的消息，进而去此消息。

顺序消息

顺序消息的意思是，消息可以按照进出队列一样，先进先出。例如：用户下单购买一件商品，需要进行创建订单、付款等操作。创建订单和付款两个操作必须按照顺序来。

RocketMQ分全局顺序、分区顺序。

  • 全局顺序：对于指定的一个Topic，最新先进先出的顺序进行发布和消费。试用于性能要求不高，需要严格按照顺序的场景。
  • 分区顺序：对于同一个Topic，可以使用sharding key 进行区块分区。每个分区上按照先进先出的顺序，进行发布和消费消息。适用于性能要求高，以sharding key 进行区块分区，在每个分区上遵循FIFO的场景。

消息过滤

RocketMQ可以根据Tag进行过滤，可以自定义属性过滤。消息过滤在Broker端实现，可以减少对Consumer端无用消息的传输，但实现起来比较复杂。

消息可靠性

RocketMQ支持消息的高可靠，影响消息可靠性的几种情况：

  1. Broker非正常关闭
  2. Broker异常Crash
  3. OS Crash
  4. 机器掉电，但是能立即恢复供电情况
  5. 机器无法开机（可能是cpu、主板、内存等关键设备损坏）
  6. 磁盘设备损坏

1)、2)、3)、4) 四种情况都属于硬件资源可立即恢复情况，RocketMQ在这四种情况下能保证消息不丢，或者丢失少量数据（依赖刷盘方式是同步还是异步）。

5)、6)属于单点故障，且无法恢复，一旦发生，在此单点上的消息全部丢失。RocketMQ在这两种情况下，通过异步复制，可保证99%的消息不丢，但是仍然会有极少量的消息可能丢失。通过同步双写技术可以完全避免单点，同步双写势必会影响性能，适合对消息可靠性要求极高的场合，例如与Money相关的应用。RocketMQ从3.0版本开始支持同步双写。

至少一次

至少一次(At least Once)指每个消息必须投递一次。Consumer先Pull消息到本地，消费完成后，才向服务器返回ack，如果没有消费一定不会ack消息

回溯消费

回溯消费是指Consumer已经消费成功的消息，由于业务上需求需要重新消费，要支持此功能，Broker在向Consumer投递成功消息后，消息仍然需要保留。并且重新消费一般是按照时间维度，例如由于Consumer系统故障，恢复后需要重新消费1小时前的数据，那么Broker要提供一种机制，可以按照时间维度来回退消费进度。RocketMQ支持按照时间回溯消费，时间维度精确到毫秒。

事务消息

RocketMQ事务消息（Transactional Message）是指应用本地事务和发送消息操作可以被定义到全局事务中，要么同时成功，要么同时失败。RocketMQ的事务消息提供类似 X/Open XA 的分布事务功能，通过事务消息能达到分布式事务的最终一致。

定时消息

定时消息（延迟队列）是指消息发送到broker后，不会立即被消费，等待特定时间投递给真正的topic。定时消息会暂存在名为SCHEDULE_TOPIC_XXXX的topic中，并根据delayTimeLevel（延时等级）存入特定的queue，时间达到，会将此消息放入真实的Topic中。

消息重试

Consumer由于某种情况down机了，导致无法消费消息，RocketMQ会将此消息进行重试操作，直到消息可以被正常消费。

会将重复投递的消息保存在一个Topic名称为“%RETRY%+consumerGroup”的重试队列，若多次重试依旧无法消费，会依次增加发送延时，将延时的消息保存在名为SCHEDULE_TOPIC_XXXX的topic中，延时到了之后，在重新投递到重试队列中。

消息重投

Producer投递消息到Broker，由于网络抖动或Broker某个节点挂掉导致消息投递失败，则会触发消息重投机制。重投机制可以会出现消息重复消费的情况。

  • retryTimesWhenSendFailed：同步发送失败重投次数，默认为2，下次重试投递的时候尝试其它Broker，尝试次数上限会抛出异常，Producer客户端来保证消息成功投递。可以本地将投递的消息保存到数据库，若投递成功则删除，反之继续投递。
  • retryTimesWhenSendAsyncFailed：异步发送失败重试次数，异步重试不会选择其他broker，仅在同一个broker上做重试，不保证消息不丢。也可以根据投递状态，进行数据库定时补偿。
  • retryAnotherBrokerWhenNotStoreOK：消息刷盘（主或备）超时或slave不可用（返回状态非SEND_OK），是否尝试发送到其他broker，默认false。十分重要消息可以开启。此配置关闭时，非投递时产生异常情况下，会忽略retryTimesWhenSendFailed配置。

流量控制

生产者流控：Broker处理能力达到瓶颈；消费者流控：消费者处理能力达到瓶颈。

生产者流控：

  • commitLog文件被锁时间超过osPageCacheBusyTimeOutMills时，参数默认为1000ms，返回流控。
  • 如果开启transientStorePoolEnable == true，且broker为异步刷盘的主机，且transientStorePool中资源不足，拒绝当前send请求，返回流控。
  • broker每隔10ms检查send请求队列头部请求的等待时间，如果超过waitTimeMillsInSendQueue，默认200ms，拒绝当前send请求，返回流控。
  • broker通过拒绝send 请求方式实现流量控制。

注意，生产者流控，不会尝试消息重投。

消费者流控：

  • 消费者本地缓存消息数超过pullThresholdForQueue时，默认1000。
  • 消费者本地缓存消息大小超过pullThresholdSizeForQueue时，默认100MB。
  • 消费者本地缓存消息跨度超过consumeConcurrentlyMaxSpan时，默认2000。

消费者流控的结果是降低拉取频率。

死信队列

当某一条消息无法进行消费时，比如消息重试次数达到上线，RocketMQ并不会将此消息丢弃，而放到死信队列中。可以通过Console控制台重新对死信队列中的消息进行消费。

  1. 用户下单并支付
  2. 订单服务发送半消息给MQ，并查询订单状态，若已支付则返回成功状态至第三方支付，否则返回错误，等第三方支付回调重试
  3. 执行本地事务，修改订单状态为已支付，执行commit/rollback状态到MQ
  4. 若第3步提交本地事务状态到MQ失败（可能由于网络原因），MQ进行事务状态回查，执行第3步操作
  5. 提交commit到MQ，会员服务消费消息。 提交rollback到MQ，消息无法被下游服务消费

概述

概念

  1. 消息模型（Message Model）

    RocketMQ主要由 Producer、Broker、Consumer 三部分组成，其中Producer 负责生产消息，Consumer 负责消费消息，Broker 负责存储消息。Broker 在实际部署过程中对应一台服务器，每个 Broker 可以存储多个Topic的消息，每个Topic的消息也可以分片存储于不同的 Broker。Message Queue 用于存储消息的物理地址，每个Topic中的消息地址存储于多个 Message Queue 中。ConsumerGroup 由多个Consumer 实例构成。

  2. 消息生产者（Producer）

    负责生产消息，一般由业务系统负责生产消息。一个消息生产者会把业务应用系统里产生的消息发送到broker服务器。RocketMQ提供多种发送方式，同步发送、异步发送、顺序发送、单向发送。同步和异步方式均需要Broker返回确认信息，单向发送不需要。

  3. 消息消费者（Consumer）

    负责消费消息，一般是后台系统负责异步消费。一个消息消费者会从Broker服务器拉取消息、并将其提供给应用程序。从用户应用的角度而言提供了两种消费形式：拉取式消费、推动式消费。

  4. 主题（Topic）

    表示一类消息的集合，每个主题包含若干条消息，每条消息只能属于一个主题，是RocketMQ进行消息订阅的基本单位。

  5. 代理服务器（Broker Server）

    消息中转角色，负责存储消息、转发消息。代理服务器在RocketMQ系统中负责接收从生产者发送来的消息并存储、同时为消费者的拉取请求作准备。代理服务器也存储消息相关的元数据，包括消费者组、消费进度偏移和主题和队列消息等。

  6. 名字服务（Name Server）

    名称服务充当路由消息的提供者。生产者或消费者能够通过名字服务查找各主题相应的Broker IP列表。多个Namesrv实例组成集群，但相互独立，没有信息交换。

  7. 拉取式消费（Pull Consumer）

    Consumer消费的一种类型，应用通常主动调用Consumer的拉消息方法从Broker服务器拉消息、主动权由应用控制。一旦获取了批量消息，应用就会启动消费过程。

  8. 推动式消费（Push Consumer）

    Consumer消费的一种类型，应用不需要主动调用Consumer的拉消息方法，在底层已经封装了拉取的调用逻辑，在用户层面看来是broker把消息推送过来的，其实底层还是consumer去broker主动拉取消息。

  9. 生产者组（Producer Group）

    同一类Producer的集合，这类Producer发送同一类消息且发送逻辑一致。如果发送的是事务消息且原始生产者在发送之后崩溃，则Broker服务器会联系同一生产者组的其他生产者实例以提交或回溯消费。

  10. 消费者组（Consumer Group）

    同一类Consumer的集合，这类Consumer通常消费同一类消息且消费逻辑一致。消费者组使得在消息消费方面，实现负载均衡和容错的目标变得非常容易。要注意的是，消费者组的消费者实例必须订阅完全相同的Topic。RocketMQ 支持两种消息模式：集群消费（Clustering）和广播消费（Broadcasting）。

  11. 集群消费（Clustering）

    集群消费模式下，相同Consumer Group的每个Consumer实例平均分摊消息。

  12. 广播消费（Broadcasting）

    广播消费模式下，相同Consumer Group的每个Consumer实例都接收全量的消息。

  13. 普通顺序消息（Normal Ordered Message）

    普通顺序消费模式下，消费者通过同一个消息队列（ Topic 分区，称作 Message Queue） 收到的消息是有顺序的，不同消息队列收到的消息则可能是无顺序的。

  14. 严格顺序消息（Strictly Ordered Message）

    严格顺序消息模式下，消费者收到的所有消息均是有顺序的。

  15. 消息（Message）

    消息系统所传输信息的物理载体，生产和消费数据的最小单位，每条消息必须属于一个主题。RocketMQ中每个消息拥有唯一的Message ID，且可以携带具有业务标识的Key。系统提供了通过Message ID和Key查询消息的功能。

  16. 标签（Tag）

    为消息设置的标志，用于同一主题下区分不同类型的消息。来自同一业务单元的消息，可以根据不同业务目的在同一主题下设置不同标签。标签能够有效地保持代码的清晰度和连贯性，并优化RocketMQ提供的查询系统。消费者可以根据Tag实现对不同子主题的不同消费逻辑，实现更好的扩展性。

架构

  • Producer：消息发布的角色，支持分布式集群方式部署。Producer通过MQ的负载均衡模块选择相应的Broker集群队列进行消息投递，投递的过程支持快速失败并且低延迟。
  • Consumer：消息消费的角色，支持分布式集群方式部署。支持以push推，pull拉两种模式对消息进行消费。同时也支持集群方式和广播方式的消费，它提供实时消息订阅机制，可以满足大多数用户的需求。
  • NameServer：NameServer是一个非常简单的Topic路由注册中心，其角色类似Dubbo中的zookeeper，支持Broker的动态注册与发现。主要包括两个功能：Broker管理，NameServer接受Broker集群的注册信息并且保存下来作为路由信息的基本数据。然后提供心跳检测机制，检查Broker是否还存活；路由信息管理，每个NameServer将保存关于Broker集群的整个路由信息和用于客户端查询的队列信息。然后Producer和Consumer通过NameServer就可以知道整个Broker集群的路由信息，从而进行消息的投递和消费。NameServer通常也是集群的方式部署，各实例间相互不进行信息通讯。Broker是向每一台NameServer注册自己的路由信息，所以每一个NameServer实例上面都保存一份完整的路由信息。当某个NameServer因某种原因下线了，Broker仍然可以向其它NameServer同步其路由信息，Producer和Consumer仍然可以动态感知Broker的路由的信息。
  • BrokerServer：Broker主要负责消息的存储、投递和查询以及服务高可用保证，为了实现这些功能，Broker包含了以下几个重要子模块。
    1. Remoting Module：整个Broker的实体，负责处理来自Client端的请求。
    2. Client Manager：负责管理客户端(Producer/Consumer)和维护Consumer的Topic订阅信息。
    3. Store Service：提供方便简单的API接口处理消息存储到物理硬盘和查询功能。
    4. HA Service：高可用服务，提供Master Broker 和 Slave Broker之间的数据同步功能。
    5. Index Service：根据特定的Message key对投递到Broker的消息进行索引服务，以提供消息的快速查询。

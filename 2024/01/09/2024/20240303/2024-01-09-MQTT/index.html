简述

MQTT（Message Queuing Telemetry Transport，消息队列遥测传输协议），是一种基于发布/订阅（publish/subscribe）模式的”轻量级”通讯协议，该协议构建于TCP/IP协议上，由IBM在1999年发布。MQTT最大的优点在于，可以用极少的代码和带宽，为远程连接的设备提供可靠的消息服务。作为一种低开销、低带宽占用的即时通讯协议，在物联网、小型设备和移动应用等方面有着比较广泛的应用。

设计规范

由于物联网的环境是非常特别的，所以MQTT遵循以下设计原则：

  1. 精简，不添加可有可无的功能
  2. 发布/订阅（Pub/Sub）模式，方便消息在传感器之间传递
  3. 允许用户动态创建主题，零运维成本
  4. 把传输量降到最低以提高传输效率
  5. 把低带宽、高延迟、不稳定的网络等因素考虑在内
  6. 支持连续的会话控制
  7. 理解客户端计算能力可能很低
  8. 提供服务质量管理
  9. 假设数据不可知，不强求传输数据的类型与格式，保持灵活性

版本

MQTT主要由两个版本：V3、V5。V5是在V3版本上做的升级，所以完全兼容V3，建议使用V5版本，可以使用更加完善的功能。

特性

  1. 使用发布/订阅信息模式，提供一对多的信息发布，使应用程序之间解耦。

  2. 屏蔽负载内容的信息传输。

  3. 使用TCP/IP提供网络连接

    MQTT协议处于应用层协议，而传输层协议还是使用的TCP/IP协议。但也有基于UDP的版本，MQTT-SN。

  4. 有三种消息发布服务质量QoS（Quality of Service）

    只有一次（Qos0）：消息只发送一次

    消息只发送一次，不管是否发送成功。发送端不会检查发送的消息是否被正确接收。

    在网络极其稳定的情况下，一般不会出现问题。但大多数情况网络情况会受多种因素干预，不能保证消息被正常的接收。所以比较适用于传输不重要消息的场景

    至少一次（Qos1）：消息最少发一次

    消息至少会发送一次，发送端需要等待接收端返回PUBACK报文确认报文。由于回应报文处于网络原因长时间接收不到，发送端会再次发送一次消息，直到收到确认报文。

    接收端会出现收到重复消息的情况，所以需要保证幂等。

    至多一次（Qos2）：保证消息收到一次

    确保接收端只接收一次消息，但发送的过程变的更加复杂，需要两次消息确认。因此，Qos2是最安全的服务等级，也是效率最低的，可以用来传输重要的数据。

    1. 发送端发送消息给Broker
    2. Broker收到发送端发送的消息，返回PUBREC给发送端，代表我收到消息了
    3. 发送端接收到PUBREC之后，发送PUBREC，表示此次发送结束
    4. Broker收到PUBREC，返回PUBCOMP给发送端，表示结束了，我知道了。

  5. 小型传输，费用小(固定长度的头部为2字节)，协议交换最小化，减少网络流量

  6. 使用LastWill和Testament特性，通知各客户端异常中断的机制

原理

实现方式

MQTT协议中三种身份：发布者（Publish）、代理（Broker）、订阅者（Subscribe）。发布者和订阅者都是属于客户端，代理属于服务器端。

MQTT传输的消息分为两部分：

  • Topic，跟消息队列的Topic类似，订阅者可以订阅改主题的消息，一旦发布者生产了此主题的消息，订阅者会收到此消息。
  • payload，订阅者具体要使用的内容，也就是消息的内容。

MQTT客户端

  • 发布其他客户端可能会订阅的信息
  • 订阅其他客户端发布的消息
  • 退订或删除应用程序的消息
  • 断开与服务器的连接

MQTT服务端

  • 接收来自客户端的网络连接
  • 接收客户端发布的消息
  • 处理客户端的订阅和退订
  • 转发消息

订阅、会话、主题

  • 订阅（Subscription）

    一个会话可以包含多个订阅。每一个会话中的每个订阅都有一个不同的主题筛选器。

  • 会话（Session）

    服务器与客户端连接之后就是一个会话了，会话包含了多个连接。

  • 主题名（Topic Name）

    消息的一个标签，代表此消息是干什么的。如订阅空调的温度，那么订阅温度就是一个主题了。

  • 主题筛选器（Topic Filter）

    对主题的通配符进行筛选，可以匹配对应的主题

  • 负载（Payload）

    消息内容

MQTT协议数据包结构

MQTT协议中，一个MQTT数据包有三部分组成：固定头、可变头、消息体。

  • 固定头，存在所有的MQTT数据包中，表示数据包类型以及数据包的分组类标识。
  • 可变头，存在于部分MQTT数据包中，数据包的类型决定了数据包中是否有可变头。
  • 消息体，存在于部分的MQTT数据包中，也就是实际的内容。

固定头

数据包类型

7-4bits：表示也就是报文类型，总共4位，无符号号值。

PINGRESP 13 心跳响应

Reserved 15 保留（禁止使用）

标识位

byte1中的3-1bits

  • DUP：发布消息的副本。用来保证数据传输的可靠性。如果设置为1，则在可变头中添加MessageId，并且需要回复确认，保证消息传输完成。

  • QoS：消息服务质量

  • RETAIN：保留标识，标识服务器需要保留这次推送的信息，如果有新的订阅者，将消息推送他。

PUBREL 保留 0 0 1 0
PUBCOMP 保留 0 0 0 0

UNSUBACK 保留 0 0 0 0

剩余长度

byte2。

固定头的第二个字节用来保存可变头的头部和消息体的长度。前七位报文长度，最高位用于标识。如果标识位1时，标识长度不够用，需要继续向下扩展空间，最多4字节。

可变报头

可变报头根据固定报头里面的报文类型，是可变的，一般包含和报文类型相关的数据。例如客户端连接报文（CONNECT），包含了协议名、协议级别、连接标志和保持连接。

协议名

MSB：大端 LSB：小端

主要指明使用的协议名，也就是MQTT

bits 说明 7 6 5 4 3 2 1 0
byte1 长度MSB(0) 0 0 0 0 0 0 0 0
byte2 长度LSB(4) 0 0 0 0 0 0 1 0
byte3 ‘M’ 0 1 0 0 1 1 0 1
byte4 ‘Q’ 0 1 0 1 0 0 0 1
byte5 ‘T’ 0 1 0 1 0 1 0 0
byte6 ‘T’ 0 1 0 1 0 1 0 0

协议级别

表示协议的版本号。对于3.1.1版本的协议，协议级别的字段是4

bits 说明 7 6 5 4 3 2 1 0
byte7 level(4) 0 0 0 0 0 1 0 0

连接标志

bits 7 6 5 4 3 2 1 0
byte8 User Name Flag Password Flag Will Retain Will QoS Will Flag Clean Session Reserved

Reserved：保留字段，为0表示连接验证通过，1表示断开客户端连接

Clean Session：清理会话标志，为0表示可以重用此会话，表示沟通继续。为1表示每次连接都要产生一个新的会话

Will Flag：遗嘱标志。当客户端在保持连接时未通讯或未发送DISCONNECT报文而关闭连接等情况时，改标志位为1，会将客户端连接时生产的遗嘱消息进行发布。如果客户端正常发送了DISCONNECT报文，则遗嘱消息会被删除。

Will QoS：遗嘱消息的服务等级

Will Retain：遗嘱保留。当Will Flag为0时。Will Retain也只能为0。当Will Flag为1时，Will Retain为0表示服务器必须将遗嘱消息当做非保留消息发布，为1时，表示服务器必须将遗嘱消息当做保留消息发布。

保留消息就是将消息保存在服务器，当订阅此消息的客户端从离线转到上线之后，会保证此消息正确的消费。

非保留消息就是直接将消息发布，然后删除。如果订阅此消息的客户端处于离线状态，那么此消息就会丢失。

Password Flag：为1时荷载中包含密码，为0反之。

User Name Flag：为1时荷载中包含用户名，为0反之。

保持连接

客户端和服务器保持连接的方式，在规定的时间内，发送PINGREQ报文，在一定时间内需要收到PINGRESP报文，否则断开与服务器的连接。
